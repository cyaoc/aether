# 行为参考

当前行为的详细说明，从 README 移出。使用方法见 [README](../README.md)，术语见 [GLOSSARY](../GLOSSARY.md)。

## 设置文件

顶层 `format_version` 是程序维护的格式版本，当前为 `1`，不是设置项，GUI 不显示。缺失时按版本 0 检查：0.2.x 的旧分组和大航海身份写法会自动升级，保留用户值、注释、未知键、编码和 BOM；没有旧分组的文件不加版本。缺少的新分组仍自动补写。升级失败时文件不动，日志和设置页显示原因，连接直播间前需修正，下次读取会重试。版本无效或高于当前程序时拒绝读取且不改写，请修正版本或使用更新程序。

CLI 和 GUI 共用 bot 设置文件 `data/aether.yml`（数据目录位置见下文“数据目录与数据库”）。首次运行时自动生成带中文注释的模板，默认值是生效的行：

```yaml
format_version: 1
log:
  retention_days: 30
  level: Information
blind_box:
  enabled: true
  daily_keyword: 今日盲盒
  monthly_keyword: 本月盲盒
  announce: true
send:
  interval_seconds: 1
welcome_danmaku:
  enabled: false
  texts: ["欢迎{大航海}{昵称}"]
  uids: []
  fan_club_level: 0
  guard: 1
  wealth_level: 0
entry_animation:
  enabled: false
  fan_club_level: 30
  volume: 80
gift_animation:
  enabled: false
  tier_30_spend: 100
  tier_40_spend: 500
  tier_50_spend: 2000
  tier_60_spend: 10000
gift_board:
  enabled: false
  threshold: 100
  threshold_by: 1
  mascot: true
  reset_on_live: true
  volume: 60
web_service:
  port: 17890
entry_animation_viewers:
```

`log.retention_days` 是日志保留天数，必须为正整数，默认 30；`log.level` 是文件日志最低级别，
可选 Trace、Debug、Information、Warning、Error、Critical，默认 Information。日志设置在进程启动时读取，修改后重启生效。

缺少的项使用默认值；未知键会列在警告中，仍照常运行。设置格式遵循 [ADR 0004](adr/0004-settings-file-line-editing.md)：
英文 snake_case 键，分组下每个设置占一行。有效的多行标量仍可读取，但多行写法、嵌套结构和行内分组标为不能逐行编辑；
日志两项只接受整数或级别名，盲盒开关只接受布尔值，不接受嵌套对象。
已知分组和设置名不能重复，即使键使用了不同的 YAML 标签；错误会定位到重复项，保存时文件保持不变。

每次开始新的直播间连接前，Core 重新读取并校验设置。有错就返回文件路径、行号和设置名，不发起网络请求、不重试；
同一个直播间连接中的重连不重新读取。YAML 语法或整体结构错误标为 `YAML`，文件读写错误标为 `文件`（第 1 行）。
启动时文件有错，日志仍按默认值接入，并在日志中记下错误。CLI 的 `login` 和 `logout` 在 stderr 输出一行警告后照常运行，
`watch` 输出错误并以非零退出码结束；GUI 照常启动，点“连接”时显示拒绝原因。修好文件后可以再次连接。`data/gui.yml` 仍只保存 GUI 显示设置，行为不变。

## 盲盒统计

`blind_box.enabled` 只接受 `true` 或 `false`，默认 `true`，关闭后既不记录，也不回复和播报；下次观看直播间时生效，自动重连不重新读取。
启用时把 V1 `SEND_GIFT` 和 V2 `SEND_GIFT_V2` 的 gold 盲盒记入 `data/aether.db`，不保存原始消息（要核对金额，把 `log.level` 设为 `Trace`；升级后，旧版本记下的原文会被删掉）；金额为整数金瓜子，
投入按 `total_coin`、开出价值按 `price × num`。相同 `tid` 只记录一次：内容也相同时视为重复推送，警告里带上被忽略的开出礼物、个数和投入；内容不同时警告 `tid` 可能不是按礼物项唯一，金额可从警告补回。数字形式的 `tid` 按其数字文本保存。以下情况都未实测确认，所以在默认日志级别下可见：uid 为 0 的盲盒（可能是神秘人）不记录，记一条 Information；带 `blind_gift` 但不是 gold 的礼物不记录并警告；`switch` 为 false 的盲盒照常记录并警告。
每条消息按 cmd 选择版本，V2 的每个 `gift_list` 项各记一行，兼容 `data.pb` 和 `data.data.pb`；损坏消息写 Warning 后跳过，继续接收后续消息。不累计 `COMBO_SEND` / `COMBO_END`。每条记录的观众、礼物和金额可在 Information 日志中查看。

启用盲盒统计时，观众发送整条关键字（默认“今日盲盒”或“本月盲盒”，忽略弹幕首尾空白），bot 会 @回复这位观众在本直播间、
收到关键字时的北京时间自然日或自然月内的投入与盈亏。本月范围从 1 日 0 点到下个月 1 日 0 点，不含结束时刻。
只统计连接期间记录的盲盒，日期按固定 UTC+8 和礼物送出时间计算。
今日回复为“今日投入X电池 赚Y电池”“今日投入X电池 亏Y电池”“今日投入X电池 不赚不亏”或“今日没有盲盒记录”，
本月回复使用“本月”前缀，例如“本月投入X电池 赚Y电池”或“本月没有盲盒记录”。
1 电池 = 100 金瓜子，先四舍五入到一位小数，整数不带小数点；盈亏四舍五入后为 0 时写“不赚不亏”。账号自己发关键字也会触发；uid 为 0 时跳过并写 Debug 日志。
`blind_box.daily_keyword` 和 `blind_box.monthly_keyword` 必须为非空的一行文字，不能通过留空单独关闭一种查询；要关闭查询，用 `blind_box.enabled` 全部关闭。
`send.interval_seconds` 必须为正整数，默认 1 秒。关键字和弹幕都先去掉首尾空白再比较；两个关键字相同时只回复今日。
这些设置均在下次观看直播间时生效。回复在发送时才查询金额，所以排队期间收到的同一天或同一个月的盲盒也会计入；查询范围仍由收到关键字的时间决定。

`blind_box.announce` 只接受 `true` 或 `false`，默认 `true`，下次观看直播间时生效。开启时，观众停手 3 秒没再送盲盒，
bot 主动 @播报这一轮的投入和盈亏，例如“本次投入300电池 亏50电池”。不同种类的盲盒合并计算，金额口径和取整与查询一致；
只计入新记录的盲盒，重复 `tid` 和 uid 为 0 的礼物不计入，账号自己送的也会播报。只关闭 `announce` 仍会记录和回复查询。
播报和查询共用发送队列，按进入队列的先后发送、遵守相同的发送间隔和失败规则；同一观众最多各有一条今日查询、本月查询和播报在排队，互不合并。
播报在每次实际发送前计算金额，排队、等待重试或被重连打断后补发时都会计入新收到的盲盒；成功或最终放弃后，本次报出的金额结束，放弃的金额不进下一轮，发送请求进行中收到的新盲盒按自己的到达时间开始下一轮。
静默等待和排队都跨自动重连保留；主动断开或换直播间时一起清空，未满 3 秒的轮次也计入丢弃条数。
成功日志写“播报观众”，以便与“回复观众”区分；正文超长时按接口失败放弃，不截断。
播报只带观众的 `reply_mid`，不带 `replay_dmid`；网页端和 App 的 @显示已在真实直播间人工验收（[#65](https://github.com/cyaoc/aether/issues/65)）。

## 发送队列

发送队列不阻塞接收和心跳，自动重连时保留待发弹幕，连正在发送、被重连打断的那条也会在重连后重发；直播间连接结束时清空并记录丢弃条数，被打断的那条也计入，不算发送失败。弹幕的 uid 或回复用的 id 读不出时，弹幕照常显示：uid 读不出就不触发回复，id 读不出就不带 `replay_dmid` 回复。
同一观众最多同时排着一条今日查询和一条本月查询；同一种查询在排队或发送时再次触发会合并，保留第一次触发的信息；查询回复成功后可立即再次触发，照常排队。
发送间隔从上一条发送结束时算起。相同正文（`msg`，不看 @ 的对象）还要距上次发送结束满 5 秒，两条规则取较晚的时刻；5 秒固定，不另设设置项。失败、被限流和被重连打断的尝试也计时，因为请求可能已经到了 B站。等待后重新计算正文，并按新正文再次检查；后面的不同正文不插队。
成功写 Information；遇到频率类失败（code 为 `10031`、`10030`，或 code 为 0 且 message 为 `msg in 1s`、`msg repeat`），写一条 Warning（带 B站 返回的 code、message 和重试等待秒数），这条保留在队首，等一个发送间隔后重试一次，重试也受相同正文规则约束。Warning 的秒数按正文不变计算，即发送间隔与 5 秒中较大的值。重试仍失败则写 Warning 并丢弃，再按两条规则继续后面的弹幕。发送间隔、相同正文计时和重试状态在自动重连后保留，直播间连接结束时清空；被重连打断的尝试不占用重试次数。其他接口拒绝（如 `1003212`）、code 为 0 时的其他非空 message（如 `f`）或网络失败直接写 Warning 并丢弃，不重试。

## 进场欢迎

`welcome_danmaku.enabled` 默认 `false`，开启后，观众进场时满足任意一个欢迎条件就发一条欢迎弹幕：UID 在 `uids` 中、本直播间粉丝团等级达到 `fan_club_level`、大航海身份达到 `guard` 档位，或荣耀等级达到 `wealth_level`。同时命中多个条件也只欢迎一次，日志按 UID > 粉丝团等级 > 大航海身份 > 荣耀等级记录第一个命中的条件。
`uids` 是正整数（int64）的单行列表，例如 `[12345, 67890]`，默认 `[]`，表示不按 UID 欢迎。`fan_club_level` 和 `wealth_level` 是非负整数，达到门槛（含门槛本身）就命中，默认 `0`，表示不按该等级欢迎。粉丝团只认进场时佩戴的本直播间主播的粉丝团，灯牌熄灭也算；戴着别的主播粉丝团的观众不按粉丝团等级欢迎。`guard` 可选 0（关闭）、1（舰长及以上）、2（提督及以上）、3（总督），默认 1。
处理 `INTERACT_WORD_V2`、`ENTRY_EFFECT`、`ENTRY_EFFECT_MUST_RECEIVE` 的进场通知，uid 为 0 时不欢迎。同一直播间连接中，同一位观众的非零 `trigger_time` 和上一次相同时只保留先到的通知，Debug 日志记录丢掉的消息类型；0 不合并，自动重连保留上一次记录，新直播间连接重新开始。合并后的进场同时交给进场欢迎和欢迎动画；不从在线榜推断进场。特效的身份取自 `uinfo`，粉丝团等级只认 `medal.ruid == target_id`（本直播间主播）的粉丝团。进场欢迎或欢迎动画开启时，每个直播间连接首次收到带版本的进场格式、或版本切换时记一条 Information；每种不认识的 cmd 各警告一次“进场消息格式可能变了”；两者都关闭时既不解码进场消息，也不记录或警告进场消息格式。
`welcome_danmaku.texts` 是单行欢迎语列表，例如 `["欢迎{大航海}{昵称}", "{@}欢迎回家"]`，默认 `["欢迎{大航海}{昵称}"]`，只有一条也写成列表。每次欢迎纯随机挑一条，可以和上次重复；每条都必填，列表不能为空，也不能只有 `{@}`。支持 `{@}`（只能放开头，发送时 @观众）、`{昵称}`、`{大航海}`；花括号本身用 `{{` 和 `}}`。每条加双引号，文字里的双引号和反斜杠分别写成 `\"` 和 `\\`。英文、数字、半角符号算 1，其他字符算 2（按 Unicode 码点计数）。上限自动读取账号的：开启进场欢迎时，每次连接直播间（包括重连）从 B站 读取，失败时按 20 处理并记一条警告。`{@}` 不占字数；昵称太长时从尾部按码点截短，不加省略号。昵称截到空后正文仍超过上限，或拼出来的正文为空时（例如只写 `{大航海}` 而观众不是大航海身份），不进入发送队列，记一条警告，“最近欢迎”显示原因，不换一条重试。旧的 `welcome_danmaku.text` 只记未知键警告，欢迎语使用 `texts` 的默认值；不迁移旧值。
已有 `welcome` 分组缺少 `texts` 时沿用 ADR 0004：读取时使用默认值，修改欢迎语并保存时才补写该项；缺整个分组时补写模板。
欢迎在进队时定好正文，和查询、播报按进队顺序发送，沿用发送间隔、同正文 5 秒等待和失败规则；不按观众合并。每次尝试（含重试）前，距进场到达已满 30 秒的欢迎会丢弃并记日志。跨重连保留，直播间连接结束时清空并计数。CLI 的 stderr 日志显示“进场欢迎”和“发送弹幕成功：欢迎观众”；这些设置在下次观看直播间时生效，可在设置文件或 GUI 侧栏的“进场欢迎”页修改。

## 动画

### 进场时播什么

`entry_animation.enabled` 默认 `false`，进场动画和欢迎动画共用这个开关。一次进场只取第一个：

1. UID 在动画名单 `entry_animation_viewers` 里：按这一行的值播。视频文件名播欢迎动画；30、40、50、60 播这一档，不看粉丝团等级；`0` 不播。
2. `entry_animation.fan_club_level` 大于 0，且本直播间粉丝团等级达到它：向下取整到 30、40、50、60，60 封顶。默认 30，0 表示不按等级。
3. 都不是：不播。

舰长、提督、总督这一版都播一般人动画。动画和欢迎弹幕各管各的，同一位观众可以两样都有。`entry_animation.volume` 默认 80，接受 0–100，进场动画、欢迎动画和送礼动画共用，取实际推送时的最新设置。GUI 里的音量都是拉杆，小喇叭加一根 180 宽的拉杆，不显示数字，拉到最左就是 0（不响）；键盘左右键每次调 1，翻页键每次调 10。
推流软件不支持 WebGL 时这一次回报失败，原因是“推流软件不支持 WebGL”；动画的脚本、贴图或声音加载失败、运行出错时也只有这一次失败，下一次重新加载，`<video>` 播放不受影响。

### 视频页和播放队列

网页服务独立使用 `web_service.port`，默认 `17890`，接受 1–65535。
旧键 `welcome_animation.port` 只记未知键警告，不迁移；旧视频目录也不迁移。缺少 `web_service` 整组时自动追加模板，已有分组中缺 `port` 时读取默认值、保存时补写。
`entry_animation_viewers` 的每行是 `UID: 值`；UID 是 int64 范围内的正整数，值是 0、30、40、50、60 或 `.mp4`、`.webm` 文件名，
文件名不能包含路径。文件放在 `data/videos/`；找不到时只警告，该观众不播放。空分组表示没有观众。
无效 UID 或文件名会报告所在行。Core 支持保留周围注释的添加、替换和整行删除。

网页服务提供视频页 `/video`、抽奖页 `/lottery` 和礼物榜页 `/gift-board`，各自在推流软件里添加浏览器素材，独立统计 SSE 连接数；`/` 返回 404。抽奖页显示报名抽奖和奖池抽奖，没有要显示的内容时透明。GUI 打开“常挂到直播画面”后，抽奖页在奖池抽奖待机、或报名抽奖结束并收起画面时，显示当前这一场没标不挂出的常挂结果；开关只在内存里，默认关，重开 GUI 回到关。
GUI 打开就启动网页服务，不需要登录或连接直播间，不跟功能开关启停。CLI 在进场动画、送礼动画或礼物榜开启的 `watch` 期间启动，并向 stdout 打印视频页地址（礼物榜开启时再打印礼物榜页地址），结束时停止。页面使用 SSE 自动重连，每 15 秒心跳一次。
视频页接收视频编号和音量，或动画编号、动画标识、昵称和音量，不接收 UID 或试播标记。视频仍按编号下载文件；回报接口是 `/video/report`。
动画名单里选了视频的观众进场就入队；bot 账号和主播不特殊处理，不受欢迎弹幕条件影响。
一次推一个视频，任意页面回报成功或失败后再推下一个；页面全部断开时不再等，最长等待 2 分钟，这两种都记为“没收到播放回报”。
从进场到轮到播放超过 30 秒就跳过（30 秒整仍可播放）。没有页面时立即跳过，不补播。
同一位观众的进场动画或欢迎动画还在排队或播放时，再次进场记“没播：上一个还没播完”，不再入队；上一个播完、失败、没播或没收到回报以后，再进场立即允许播放，不设时间间隔。
试播走同一个播放队列，不检查也不占用上述观众限制；播放中这一行显示“停止”，点击后视频页立即停止，最近播放记“已停止”，接着播队列里的下一个。真实进场播放中显示不可点击的“播放中”；CLI 不提供试播命令。开关保存为关闭后，还在用旧设置的直播间连接不再交给视频页，也不记跳过。

连接数和播放进展记 Information，播放失败和端口被占用记 Warning；端口被占用不影响直播间连接。
网页服务和状态订阅独立于直播间连接；切换动画开关、修改动画名单都不重启服务，页面保持连接。浏览器会先下载完整视频再播放，因此大视频会占用相应内存；
不转码、不抠图。使用步骤见 [README](../README.md#欢迎动画)，推流软件验证边界见 [研究记录](research/2026-10-15-welcome-animation.md)。

### 送礼动画

普通付费礼物按 `coin_type: gold` 的 `total_coin` 计投入，盲盒按盲盒投入计；免费礼物不计。
每个直播间的观众各自累计，停手 3 秒结束一轮，和一轮盲盒互不影响；自动重连保留，主动断开清空。
uid 为 0 只记录日志；目前不按 tid 去重。大航海开通、续费已接入：按实际付的价格计入一轮送礼的投入，和普通礼物在 3 秒内连着送算同一轮（算法见下一节“大航海开通和续费”）。
V2 已使用本地人气票消息验证；V1 使用 BAC 示例，未实测。批量、折扣、包裹仍缺真实样本，金额待实战 Trace 核对。
V1、V2 礼物消息还解出礼物 id、名称、单价、个数、观众头像地址、礼物图标地址和 `tid`（盲盒取它开出的礼物），供礼物榜使用：V1 缺 `face` 或 `gift_info.img_basic` 按损坏消息处理，V2 缺这两项按空地址处理。

送礼动画在一轮结束时读取最新开关和门槛，按实际投入取达到的最高一档，不要求粉丝团，也不受进场名单影响。同一观众的多轮送礼分别排队，30 秒排队时限从各轮结束时开始。GUI 可调整四档门槛、试播并查看最近播放；门槛不递增时不能保存。

三种动画试播都不看开关，要求视频页连着；欢迎动画还要求视频已保存。进场动画、送礼动画和欢迎动画共用先来先播的播放队列、30 秒排队时限和结果回报；音量取实际推送时的最新设置。

### 大航海开通和续费

观众开通、续费舰长、提督、总督时，`USER_TOAST_MSG_V2`（JSON）当作一份礼物进入一轮送礼，和普通礼物一样触发送礼动画和隐藏款。读取 `sender_uinfo.uid`、`sender_uinfo.base.name`、`sender_uinfo.base.face`（大航海消息常常不带，为空）、`guard_info.guard_level`（1 总督、2 提督、3 舰长）、`pay_info.num`、`pay_info.price`、`pay_info.unit`、`pay_info.payflow_id`、`gift_info.gift_id` 和 `option.source`。
B站 每次上舰先推一条 `source` 为 0 的、再推一条 2 的，只认 0；`GUARD_BUY` 的 `price` 永远是原价 198 元，不用。字段缺失按损坏消息处理，写 Warning 后跳过，继续接收后续消息；`guard_level` 不是 1 到 3、`num` 不是正数、`price` 或 `uid` 为负也一样。uid 为 0 只记录日志，`price` 为 0 的和免费礼物一样不算投入。

`price` 是实际付的价格，已经包含优惠，不用另算折扣：公开抓包里的 138000、168000、198000 都对得上下面的现价，2021、2022 年抓包里的 158000 是 2024 年 7 月调价前的续费价。主播提供的 B站 现价（2026-11，单位电池，10 电池 = 1 元 = 1000 金瓜子）：

| | 1 个月 | 3 个月 | 6 个月 | 12 个月 | 续费 |
| --- | ---: | ---: | ---: | ---: | ---: |
| 舰长 | 1980 | 5340 | 10380 | 20460 | 1680 |
| 提督 | 19980 | 51940 | 99880 | 195760 | 15990 |
| 总督 | 199980 | 519940 | 没提供 | 没提供 | 159990 |

舰长连续包月每月自动扣 1380。续费只能按月买。网上资料里的舰长 1580、提督 15980、总督 159980 电池是调价前的旧价。

`unit` 是“月”时 `num` 是月数，投入按下面算；三档单月原价（舰长 198000、提督 1998000、总督 19998000 金瓜子）是 `UserToastV2` 里的常量，B站 调整原价时要跟着改：

- `price` 不超过这一级的单月原价：`price` 是单价，投入 = `price × num`，个数是 `num`；
- `price` 超过这一级的单月原价：`price` 已经是总价，投入 = `price`，个数仍是 `num`；
- `unit` 不是“月”（例如“5天”）：按一次计，个数 1，投入 = `price`。

单价 = 投入 ÷ 个数（取整）。两种理解能从数值分出来：单月价和多个月折算的每月价都不超过单月原价，多个月的总价都超过它（最低的舰长 3 个月 534000）。推的如果是取整后的单价，乘回去和真实总价最多差几个金瓜子（提督 12 个月：1631333 × 12 = 19575996，真实总价 19576000）。`num` 大于 1 或 `unit` 不是“月”时，把原始的 `guard_level`、`num`、`price`、`unit` 记一条 Information 日志，上实战时核对。

未验证：
- 一次买多个月（`num` 大于 1）时 `price` 是单价还是总价：公开资料里没有抓包，blivechat 按 `price × num` 算，blivedm-go 按总价算，都没给出依据；上面的规则只是按数值区分的兼容办法；
- `unit` 不是“月”的情况：公开资料只说正常为“月”，其他内容以 `unit` 为准，没有抓包。

测试样本是按公开字段名和上面的价格表合成的，不是抓包，见[测试数据说明](../tests/Aether.Core.Tests/Fixtures/README.md#user_toast_msg_v2-合成样本)；字段来自 [blivedm](https://github.com/xfgryujk/blivedm/blob/master/blivedm/models/web.py)、[blivechat](https://github.com/xfgryujk/blivechat/blob/master/frontend/src/api/chat/ChatClientDirectWeb.js)、[sjh8130/bili_danmaku](https://github.com/sjh8130/bili_danmaku/blob/HEAD/Testing.md) 和 [BAC 的 USER_TOAST_MSG](https://github.com/pskdje/bilibili-API-collect/blob/master/docs/live/message_stream.md)，2024 年 7 月的调价见 [IT之家](https://www.ithome.com/0/780/661.htm)。

## 礼物榜

`gift_board` 分组控制礼物榜，也就是网页服务的 `/gift-board` 页面：`enabled` 默认 `false`，关闭时不记录也不显示；`threshold` 是上榜门槛（电池），必须为正整数，默认 100；`threshold_by` 是门槛比什么，`1` 比礼物单价，`2` 比同一观众同一礼物累计的总价，默认 1；`mascot` 是否显示看板娘，默认 `true`；`reset_on_live` 是否每场开播自动换一张新榜，默认 `true`；`volume` 是新的第一名那一声的音量，0–100 的整数，默认 60，0 表示不响。
缺这一组的旧文件按默认值处理，不升 `format_version`，读取时补上模板，GUI 保存时按追加规则补写。GUI 保存后立即生效（经 `AetherClient.ApplyWebSettingsAsync`），CLI 下次 `watch` 时生效。

礼物榜开着、bot 连着直播间时，把 V1 `SEND_GIFT`、V2 `SEND_GIFT_V2` 的付费礼物（盲盒按开出的礼物算）和 `USER_TOAST_MSG_V2` 的大航海开通、续费，按“一位观众的一种礼物”累计，记进 `data/aether.db` 里这个直播间最新的一期；还没有期时先开一期。礼物键是 `gift:<礼物 id>` 或 `guard:<1|2|3>`：盲盒开出的礼物和直接送的同一种礼物合并，大航海按等级一行。每行存昵称、头像地址、礼物名、礼物图标地址、单价（金瓜子）、累计个数，以及第一次和最后一次收到的时间；昵称、头像、礼物名、图标以最后一次为准，单价是累计的总投入除以总个数，所以大航海续费价和开通价不同时，价值仍是实际付的钱。时间用 Aether 收到时的时间，B站 不补发历史。礼物榜自己存一份汇总，不读 `blind_box`，两边互不影响（[ADR 0012](adr/0012-gift-board-stores-its-own-totals.md)）。
uid 为 0 的礼物（可能是神秘人，未实测）不上榜，记一条 Information。同一个直播间连接里，礼物按 `tid`、大航海按 `payflow_id` 去重：见过的第二次不计入，记一条 Warning“礼物榜：重复推送的礼物，已忽略”，带上 `tid`、礼物和个数；`tid` 为空的不去重；V1 和 V2 共用一份见过的号。号只存在内存里，自动重连保留，断开或换直播间清掉。只有 Aether 连着直播间时收到的礼物才会上榜。

显示时才按当前设置筛选，所以改门槛立即生效：比单价时，单价 ≥ 门槛就上榜；比累计总价时，单价 × 个数 ≥ 门槛就上榜，刚好等于也上榜；1 电池 = 100 金瓜子。上榜的行按单价 × 个数从高到低排，一样时第一次收到的在前。

`AetherClient.GiftBoard.GetUpdatesAsync` 先给当前状态，之后每次变化给一份完整状态，GUI 和礼物榜页用同一份：按顺序的上榜行（标识、昵称、头像地址、礼物名、礼物图标地址、大航海等级、单价、个数）、`mascot` 和 `volume`，以及 GUI 要的 `period`（这一期的开始时间 `startedAt` 和有礼物的观众数 `viewers`，不受上榜门槛限制，0 表示这一期是空的）和 `previous`（上一期的同样两项）；没有直播间连接时这两项为空，还没有期时 `period` 为空，没有上一期时 `previous` 为空，礼物榜页不用它们。礼物榜关闭、或者没有直播间连接（从没连过，或者点了“断开”）时是空列表；断线后自动重连还算同一个直播间连接，重连中状态不变；换到别的直播间时给那个直播间最新的一期。网页服务的 `gift-board` 页面把它当作 SSE 事件 `state` 推到 `/gift-board/events`，同样先推当前状态，再每次变化推一份；网页服务状态和连接日志里带上礼物榜页的推流软件连接数。

### 期

礼物榜按期记：一期就是一张榜，礼物榜页和 GUI 只显示这个直播间最新的一期，换期、清空、恢复都不删记录，旧的期留在 `gift_board_period` 里。每期存它开始的时间（Aether 开这一期的时间），和这一期所属那一场直播的开播时间 `live_time`（Unix 秒，开期时没开播则为空）。

`reset_on_live` 为 `true` 时每场开播换一张新榜，一场直播按 B站 记的开播时间区分。连上直播间时，`BilibiliApi.ResolveRoomAsync` 本来就调的 `room_init` 多读两个字段：`live_status`（0 未开播，1 直播中，2 轮播中）和 `live_time`（开播时间，Unix 秒，未开播时为 `-62170012800`，即 0001-01-01 UTC，见 [BAC 的 room_init](https://github.com/pskdje/bilibili-API-collect/blob/main/docs/live/info.md)），缺任何一个或不是数字，都按无法解析的响应处理，直接报错退出。收到 `LIVE` 消息（[BAC 的直播开始](https://github.com/pskdje/bilibili-API-collect/blob/main/docs/live/message_stream.md)，开始推流时下发，可能一次好几条，只有第一个包带开播时间，Aether 不用它）时再请求一次 `room_init`，在后台读，不拖慢接收弹幕；读取失败记一条 Warning，不影响直播间连接。`live_status` 是 1、`live_time` 不是 `-62170012800`，而且和这个直播间最新一期记的开播时间不同（最新一期没记开播时间，或者还没有期，也算不同），就开新的一期并记下这个开播时间。没开播、轮播、同一场都不换：断开再连、重复的 `LIVE`、跨过零点都不换，`LIVE` 一次推好几条也只换一次。下播后、轮播时送的礼物记进当前这一期，下一场开播才换。开播时 Aether 没开着也不要紧，连上时按 `room_init` 补判；弹幕连接断开后自动重连不再请求 `room_init`，所以断线期间开的播，要等下一条 `LIVE` 或下次连上才会换。礼物榜关着时不开期。`reset_on_live` 为 `false` 时只在清空时换。

`AetherClient.GiftBoard.Clear()` 清空：两种模式都开一个新的、空的一期；正在直播（最近一次读到的 `room_init` 是直播中）时，新的一期记下当前这一场的开播时间，同一场里重连不会再换。`Restore()` 恢复上一期：把最新一期的行按“观众、礼物键”合并进它前面最近的一期（只看这个直播间），个数相加，单价按总投入除以总个数重算，昵称、头像、礼物名、图标以最新一期的为准，第一次收到的时间取早的、最后一次取晚的，再删掉最新一期，上一期变回当前这一期，一个事务里做完；合并和累加一个礼物用的是同一段 SQL。正在直播时，恢复后的这一期记下当前这一场的开播时间；可以连续恢复，一期一期往前合并。没有上一期时恢复、没连直播间时清空或恢复，都抛 `InvalidOperationException`。清空和恢复只动当前直播间的期，不碰 `blind_box`，做完推一份新状态，礼物榜页照常重画。查看历史的期、挑某一期恢复不在范围内。

未验证：
- 断流不久又重新推流时，`room_init` 的 `live_time` 变不变：变了榜就换新（旧的期还在库里，可以恢复上一期），不变就还是同一张；
- 收到 `LIVE` 消息时，`room_init` 是否已经是直播中和新的开播时间：读到的还是旧状态时，这一场要等下一条 `LIVE` 或下次连上才换。

## GUI

GUI 使用 Fluent 主题并跟随系统深色／浅色，默认 1200×720，最小 1040×600。左侧栏放直播间卡片、功能导航和账号。
每次打开窗口先显示插画启动页，至少停留 0.6 秒，账号读取有结果后淡出 150 ms；启动页显示期间不能操作底下的页面。
读到有效账号时直接显示主界面和昵称；没有登录凭据或 B站明确说未登录时直接显示扫码登录页，扫码后才进主界面，二维码过期自动换码，出错时显示原因和“重试”。
账号请求或数据库读取失败、或 3 秒内没有结果时，进入主界面并显示“账号信息读取失败”，可重试、连接直播间、配置和试播；不会因为断网要求重新扫码，超时后的迟到结果不会切换页面。重试读到未登录时切到登录页。
网页服务与账号读取并行启动，在启动页和登录页上也运行，直播姬仍可打开视频页和抽奖页。
版本号（如 `v0.3.0`）固定在窗口左下角：主界面在侧栏账号下方，每一页都能看到；登录页在左栏步骤条下方。版本号来自 GUI 程序集的版本，发布时由 `release.yml` 用 tag 写入，本地构建显示 `v0.0.0-dev`。
输入房间号后点“连接”或回车；连接中途登录凭据失效时，内容区显示扫码卡片，
侧栏保留，扫码成功后继续连接。点“断开”可取消扫码或结束连接，再输入新的
房间号。卡片显示从首次连上开始的分钟数，自动重连不会清零。账号的 ⋯ 菜单里点“退出登录…”并确认后，
先结束当前连接或扫码，再删除凭据，然后回到扫码登录页；关闭窗口也会先取消并等待当前操作结束。
房间号输入框会预填上次连接成功的号码，也可以直接输入新号码。下拉列表按最近连接成功的顺序保留最多 5 个号码，去重后保存到 `data/gui.yml` 的 `RecentRooms`；保留输入原文，短号不会换成真实房间号。连接失败或连上前取消不记录，断开和退出登录不清空历史。
选中历史项只填入号码，不会连接；列表展开时上下键选择，回车收起，收起后再按回车才连接。启动不会自动连接，没有历史时输入框为空。历史保存失败会显示错误，不影响已经建立的连接。
点每行右侧的 ×，或在列表展开时按 Shift+Delete，可以删除该历史项并保存，框里的文字保持不变。删掉最后一项会收起列表；没有历史时不显示下拉箭头。展开或收起后光标在文字末尾，用 Tab 进入时仍全选文字。

窗口显示错误提示，日志写到文件和调试控制台。列表开启虚拟化，在底部时跟随新弹幕；往上翻看历史时暂停，

## 日志

CLI 和 GUI 的文件日志位于 `data/logs/`，默认记录 Information 及以上级别，由 `log.level` 控制。
公共日志写到 `aether-yyyyMMdd.log`，允许多个进程共享写入；解析到真实房间号后，
包括扫码和重连在内的 Core 日志写到 `<真实房间号>/aether-yyyyMMdd.log`。
直播间连接因错误结束时，该直播间的日志记下错误；CLI 或 GUI 另在公共日志记一条，房间号确定前的失败只记在公共日志。
文件按本地日期每天滚动，默认保留 30 天，由 `log.retention_days` 控制：启动时清理所有目录的过期文件，打开或滚动某组日志时再清理该组；
空直播间目录保留，避免与其他进程创建日志文件发生竞态而丢失日志。
每条写完即关闭文件，切换直播间不会积累句柄，其他进程可在断开后接管同一直播间。
每条包含时间、级别、进程号、类别和消息，异常附完整堆栈。日志同步写入，不在内存中缓冲。
进程未处理异常、未观察到的 Task 异常和 GUI UI 线程未处理异常立即记录，不标记为已处理，
仍遵循运行时原本的退出行为（未观察到的 Task 异常默认不终止 .NET 进程）。
跳过无法解析的直播间消息时，警告附原始 JSON；超过 2KB 按 UTF-8 字节截断并注明。
`log.level` 设为 `Trace` 时，每条直播间消息另记一条完整的原始 JSON，不截断，含观众的 uid、昵称等个人信息，
只在抓包时临时开启，步骤见 [测试数据说明](../tests/Aether.Core.Tests/Fixtures/README.md)。
弹幕、礼物、进场三类消息使用同一套格式日志规则：每个直播间连接首次收到带版本的格式、或版本切换时记一条 Information；
收到不认识的 cmd 时，按弹幕、礼物、进场分类警告“收到不认识的{类别}消息 {Command}，{类别}消息格式可能变了”，同一直播间连接中每个 cmd 只警告一次。
礼物格式是 V1（`SEND_GIFT`）或 V2（`SEND_GIFT_V2`），进场格式目前是 V2（`INTERACT_WORD_V2`）；进场只在进场欢迎或欢迎动画开启时记录。
自动重连保留版本和已警告 cmd 的记录，新直播间连接重新开始。

## CLI 与直播间连接

弹幕以 UTF-8 写到 stdout：`[HH:mm:ss] 昵称 [舰长][粉丝团 47][荣耀 45]: @被回复的昵称 内容`；粉丝团等级、荣耀等级、大航海身份没有时不写对应的方括号，大航海身份按实际显示舰长、提督或总督，没有被 @ 的观众时也不加 `@昵称 `。输出不使用 ANSI 颜色；状态和日志写到 stderr。
Ctrl+C 关闭连接并正常退出，错误返回非零退出码。每次 `watch` 开始直播间连接时，
先解析短号或真实房间号，成功后只使用这个真实房间号，重连不再请求 room_init（礼物榜只在收到 `LIVE` 消息时再请求一次，见“礼物榜”一节）。
解析时的临时网络失败按下面的重连节奏重试；不存在的直播间立即报错，不扫码、不连接、不重试。
随后获取直播间锁，再用保存的 cookie 调 nav 检查登录状态；没有凭据或已失效时，在 stderr 显示二维码，
扫码成功后保存凭据并继续连接，无需先运行 `login`。二维码过期自动换新，扫码期间也可按
Ctrl+C 取消。连接使用 nav 返回的 mid 和凭据中的 buvid3，HTTP 请求携带保存的 cookie，
以接收观众的真实昵称。网络失败、超时、B站 服务器 5xx 或弹幕服务器断开时，`watch`
提示“重连中”，按 1、2、4、8、16、30、30…… 秒自动重试；收到认证成功回复后重置为 1 秒。
60 秒没有收到任何数据也会重连；心跳回复正常的安静直播间不会断开。
每次重连重新获取 wbi key 和弹幕 token，中途凭据失效或被 `logout` 删除时暂停接收弹幕，
显示二维码重新登录，成功后继续连接同一个直播间。等待扫码时也会检查本地数据库，
可在另一个终端运行 `login` 或在 GUI 登录，经 nav 确认有效后恢复连接；新凭据未生效时记一条警告并重新显示二维码。扫码阶段的网络失败仍每 2 秒原地重试，
不提示“重连中”，也不作废已显示的二维码。B站 明确拒绝（错误码含房间号不存在、HTTP 4xx、
弹幕认证失败）、无法解析的 HTTP 或认证响应、损坏的弹幕帧、本地错误（如数据库）和程序缺陷，
重试也不会好转，反复请求还会加重风控，所以直接报错退出。单条直播间消息不是合法 JSON、
缺少有效 cmd，或 DANMU_MSG 取不到昵称或内容时，只跳过该条并记一条警告，能读取 cmd 时一同记录；
后续弹幕继续接收。包头无效、解压失败和协议版本不支持仍直接报错退出。重连等待期间 Ctrl+C 也会立即结束。

## 直播间锁

同一个 `data/` 中，同一个真实房间号只允许一个直播间连接（短号和真实房间号也会冲突）。
Core 独占打开 `data/room-<真实房间号>.lock`，在扫码和断线重连期间持续持有；
第二个 CLI 或 GUI 会在检查登录、显示二维码之前报“直播间 … 已有直播间连接”，不会重试。
CLI 输出“错误：……”并以非零退出码结束；GUI 显示连接错误，状态回到“未连接”。
取消、出错或释放更新流都会释放锁并删除锁文件；进程崩溃时由操作系统释放锁，
留下的锁文件在下次连接同一直播间时复用。不要在连接运行期间删除它。同一目录可同时连接不同直播间；不同数据目录互不影响。
macOS / Linux 上的锁是 flock，`data/` 应放在本地磁盘上，部分网络文件系统不支持。
`login` 和 `logout` 不获取直播间锁，观看期间可在另一个终端执行。

## 登录凭据

`login` 先打开数据库、获取 buvid3，再在 stderr 显示字符画二维码，用 B站 App 扫码并确认。
每两秒轮询一次，过期后自动打印新二维码，成功保存凭据后提示“已登录”。网络错误（连不上、
HTTP 非 2xx、超时）记一条警告，两秒后重试，直到成功或 Ctrl+C；B站返回的错误码直接报错退出。
Ctrl+C 取消并正常退出。`logout` 先调用 B站 退出登录接口，让服务器端的 SESSDATA 失效，再删除本地登录凭据，可重复执行。
B站 端退出失败（网络错误、错误码、cookie 已失效）时记一条警告，仍删除本地凭据；
Ctrl+C 取消则保留本地凭据。

连接、重连前和连接期间，距上次检查满 24 小时才检查是否需要刷新登录凭据；
只在 B站 返回 `refresh=true` 时刷新。新凭据保存后才确认作废旧凭据，确认失败只记警告。
已发出的刷新请求不随直播间连接结束而取消，连接等它保存完再重连。
检查或刷新遇到临时网络错误时保留原检查时间，连接照常，连接期间 30 秒后再试；
`cookie/info` 返回错误码、刷新页面结构变化等其他失败记一条警告，24 小时后再查，连接照常，
凭据是否有效仍由每次连接前的 nav 判断。B站 拒绝刷新请求时删除仍匹配旧 refresh_token 的凭据，
结束当前连接，转入重新登录。连接期间凭据被另一个进程删除（如 `logout`）时停止检查，当前连接照常，
下次重连时要求扫码。刷新结果不会覆盖另一个进程刚保存的凭据，也不会把已经退出的登录写回来。

## 数据目录与数据库

数据目录遵循 [ADR 0002](adr/0002-portable-data-directory.md)：Release 用程序目录下的 `data/`；
Debug 从程序目录向上寻找 `Aether.slnx`，用其所在目录下的 `data/`，找不到则退回程序目录。
与启动命令所在目录无关。SQLite 文件是 `data/aether.db`，使用 WAL；`PRAGMA user_version`
记录表结构版本，当前为 7。升级使用手写 SQL，并与版本号在同一事务中提交。
v2 升级到 v3 保留登录凭据，新增 `blind_box` 表，按真实房间号、观众 uid 和送出时间建立索引。
v3 到 v4 把抽奖表纳入版本号，保留已有表和数据；v0.2.x 已有的抽奖表结构不变。
v4 到 v5 给 `lottery_draw` 加不挂出标记 `hidden_from_stream`（开奖结果的 JSON 不变），新增 `lottery_prize_set` 存奖品方案：按直播间、抽奖方式和名称唯一，内容是一列 JSON。
v5 到 v6 删除 `blind_box` 的 `raw_message` 列：盲盒不再保存原始消息，已记下的原文随列一起删除，其余数据不变。
v6 到 v7 新增礼物榜的 `gift_board_period`（期：直播间、开始时间、所属那一场的开播时间）和 `gift_board_total`（按期、观众、礼物键累计的一行），两张表是空的，其余数据不变。
`credential` 表只存一行，保存完整 cookie 名值 JSON、refresh_token、UTC 保存时间和检查时间 `checked_at`。
v1 升级后保留原凭据，检查时间为空，下次连接立即检查；扫码或刷新保存时检查时间等于保存时间。
凭据暂存明文，`data/` 已被 Git 忽略；连接开启 `secure_delete`，删除或覆盖的凭据不会残留在文件里。
macOS / Linux 上数据库文件（含 `-wal` / `-shm`）权限为 0600，只有当前用户可读写；Windows 依赖目录继承的 ACL。
`login` / `logout` / `watch` 都会打开数据库。CLI 与 GUI 放在同一发布目录时共用这些数据。

## Core 结构与测试

Core 的业务入口都在 `AetherClient`：`LoginAsync` 返回 `LoginQrCode`、`LoggedIn` 更新流；
`LogoutAsync` 删除凭据；`WatchAsync` 返回 `WatchQrCode`（需要登录时）、`Connecting`、`Connected`、`Reconnecting`、`Danmaku`、`SendQueueUpdate` 更新流。
`SendQueueUpdate` 报告盲盒查询、盲盒播报和进场欢迎进入发送队列、开始发送、成功、等待重试、丢弃，以及欢迎命中却没进入发送队列的原因。
每项编号在进程内不重复，自动重连后沿用；连接结束不逐项报告丢弃，由外壳标记未完成的项。CLI 忽略这些更新，继续使用现有日志。
取消或释放更新流会结束对应操作。测试从这些入口驱动，注入假的 HTTP、真实 BCL WebSocket 的本地对端、
`FakeTimeProvider` 和独立临时数据目录，使用真实 SQLite，不访问 B站。真实捕获测试帧的来源与脱敏方式见
