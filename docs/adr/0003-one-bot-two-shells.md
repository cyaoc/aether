# CLI 和 GUI 是同一个 bot 的两个外壳，bot 的行为全在 Core

CLI 给专业用户在服务器上挂机，GUI 给一般桌面用户。曾考虑让 GUI 退化成启动 CLI 的启动器或设置器，但那样要设计进程间协议来传二维码、状态和弹幕，显示逻辑照样要写，代码只多不少；关掉窗口后 bot 继续跑、在桌面远程管理服务器上的 bot，这两种需求都不存在。所以 CLI 和 GUI 各自完整地运行 bot，共用 Core 和同一个 `data/`。

划分界线：凡是改变 bot 做什么、记什么的（规则、统计、读取设置、日志写到哪里），都在 Core；外壳只负责显示和收集输入。检验方法：同样的设置，换一个外壳跑，bot 的行为不能不同。显示不要求对等，每个功能的 spec 写明各外壳显示什么；CLI 是完整入口，每个功能都要能通过命令、stdout 或日志用到，直播画面功能除外（见 Consequences）。

一个进程只有一个直播间连接。同一个 `data/` 里可以同时跑多个进程连不同的直播间，共用登录凭据、设置和数据库；同一个直播间（按真实房间号）同时只允许一个直播间连接，第二个直接报错。这条用 `data/` 里每个直播间一个、由操作系统持有的锁文件实现，进程崩溃时自动释放；只在直播间连接期间持有，`login`、`logout` 不受限制。

## Consequences

- CLI 要正式支持 Linux（服务器），GUI 只支持 macOS 和 Windows。
- 抽奖只有 GUI 有，CLI 不做（2026-10-16 补充）。抽奖页要和推流软件在同一台电脑上，这种场景用的本来就是 GUI；抽奖还要主播一边直播一边点开始、截止、开奖、停，CLI 在 `watch` 时标准输出被弹幕占着，在服务器上挂着时又没有终端，另开命令去控制正在运行的进程则要设计进程间协议，这正是上面不让 GUI 当启动器的原因。抽奖的规则和记录仍放在 Core，以后真要给 CLI 补入口不用重写。
- 按类别划线（2026-11-07 补充，把上一条从抽奖扩到所有直播画面功能）：直播画面功能，也就是进场动画、欢迎动画、送礼动画、抽奖、礼物榜，以后的桌宠，只在 GUI 里有；其余的 bot 功能，弹幕、盲盒统计、欢迎弹幕、发送队列、日志，两个外壳都有。理由和抽奖一样：浏览器素材要和推流软件在同一台电脑上，还要边播边点，在服务器上挂机的 CLI 两样都做不到。CLI 不再启动网页服务，没有视频页；以前 CLI 开着进场动画或送礼动画时会开视频页，没有人这样用。设置文件仍然共用，CLI 照常读和校验直播画面功能的分组，只是不用它们（[ADR 0016](0016-config-in-settings-file-and-database.md)）。
- 一个 `data/` 只有一个账号。不同直播间要用不同账号，只能各用一份程序目录。
- 多个进程用同一个账号在不同直播间发弹幕时，如果 B站 的频率限制按账号算，进程之间需要协调发送节奏，直播间锁管不到这一点。做第一版发送队列时（盲盒统计）仍查不到频率限制是否按账号算，决定先不协调：每个进程只管自己的发送节奏，等真的出现同一个账号挂多个直播间被限流时再做。
