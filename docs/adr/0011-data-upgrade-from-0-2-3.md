# 从 0.3.x 起保证已有 data/ 能升级，起点是 0.2.x

取代 [ADR 0007](0007-no-upgrade-compat-in-0x.md)。0.x 不写升级的前提是没有用户，现在 v0.2.3 已有实际使用的数据。这份数据拿 v0.3.0 打开不报错，欢迎和动画设置却回到默认值，用户很难发现。所以改为：从 v0.3.0 之后的第一个发布版本起，0.2.x 及以后版本的 `data/` 复制到新版本要照常可用，用户的设置和记录不丢。v0.3.0 没有用户，不为它单独处理。设置文件和数据库各管各的版本和升级步骤，不做共用框架：两边相同的只有"一个版本号加一串步骤"，读写方式、事务和失败处理都不同。

## Consequences

- 改设置键、值的写法或含义，要同时写升级步骤和测试；设置文件仍按 [ADR 0004](0004-settings-file-line-editing.md) 逐行改写，保留注释和不认识的键。
- 设置文件的版本记在顶层的 `format_version`，缺失时视为 0。文件版本高于程序时报错，和数据库一样。
- 升级不改变用户已有的效果：新设置的默认值会改变效果时，升级时写入旧效果对应的值。
- 改表结构或 JSON 列格式，要在 `Database` 里加版本块并升 `user_version`。版本块可以转换旧数据，和版本号在同一事务里提交；块里不调用现在的 Store 和 record，发布后不再改。
- JSON 列的格式跟着 C# record 走（如 `lottery_draw.result`、`lottery_prize_set.content`），改属性名就是改格式，旧行读出来不报错，只是值丢失。
- 改约束或类型要重建表。`PRAGMA foreign_keys` 在事务里无效，`defer_foreign_keys` 过不了提交（`DROP TABLE` 记下的违规不会被改名抵消），所以要在事务开始前关掉升级用的连接的外键，提交前跑 `foreign_key_check`。
- 每个带格式变化的发布版本留一份冻结的测试数据，不改旧的。
- 回滚照旧：旧目录保持不动，直接运行旧程序。升级说明仍写"复制"而不是"移动" `data/`；备份是用户的事，程序不替用户备份。
- `data/gui.yml` 不升级，它读失败回到默认值，只影响显示和最近的房间号。（2026-11-07 起不再适用：GUI 把 `gui.yml` 搬进设置文件和数据库后删掉，见 [ADR 0016](0016-config-in-settings-file-and-database.md)。）
