# Core 的状态分成几个区域，每个区域一次执行一步，区域之间并行

Core 的状态原来靠 66 处 `lock` 保护，方法由谁调用就在谁的线程上跑。GUI 的视图模型各自用 `Task.Run` 挪到后台、各自排先后、各自决定关窗时等不等，出过界面线程上同步写 SQLite、启动时读回的旧值盖掉刚改的、测试偶发失败这些问题（#344）。现在把 Core 的状态按功能分成几个区域，每个区域有自己的队列，一次执行一步。一步是一个同步函数，执行时才拿到本区域的状态，在外面拿不到。不同区域之间并行。收消息、网络请求、等页面回报这些异步流程在区域外面跑，要碰状态时交一步给对应的区域：要结果就 `await 区域.Run(...)`，不等结果就 `Post`。GUI 只调用 Core 的 async 命令、订阅 Core 推来的状态，界面线程碰不到 SQLite，也碰不到 Core 的状态。每个区域对外是一个单独的门面：GUI 和 Core 里的其他类只拿得到门面，状态对象只交给区域，状态类的构造函数和实例方法都是 internal。订阅也走区域，登记和退订都是一步。

| 区域 | 管的状态 |
| --- | --- |
| 抽奖 | 当前一场抽奖、奖品方案、抽奖历史 |
| 礼物榜 | 期、选项、内存里的榜 |
| 网页服务 | 推流软件的连接、视频页、进场动画、欢迎动画、送礼动画、桌宠页 |
| 账号 | 登录凭据 |
| GUI 状态 | 最近的房间号、“只保留最近 1000 条” |
| 直播间连接 | 发送队列、一轮送礼、一轮盲盒、收礼记录的写入；每个直播间连接一个，断开就收掉 |

抽奖页、礼物榜页不存状态，只订阅抽奖、礼物榜的推送再推给推流软件。桌宠页和几种动画一样在网页服务区域，不单独成一个区域：它只存要推给页面的东西，试演要用推流软件的连接数。

## Considered Options

- 维持加锁，只在 GUI 补几处：状态还是散在各线程上，根子没动。没有选。
- Core 只有一个队列，所有状态的步骤都排在里面：结构最简单，但完全没有并行，查抽奖历史、礼物榜连上时读一整期记录都会拖住别的功能。没有选。
- Core 一条线程（自己写 `SynchronizationContext`，Core 的代码都跑在上面）：原子性靠“两个 await 之间不被打断”，是隐式的，有人在原来锁住的一段里加一个 await 就悄悄失效，编译器不报；还要禁用 `ConfigureAwait(false)`、把第三方回调搬回来，在这条线程上阻塞等待就死锁。没有选。
- 数据库挪到单独的线程，一步里 await 它：一步跨了 await 就不原子了，还得给每个功能加“正在写库”的状态来排先后，又把要删的复杂度加回来。没有选；一步里同步读写本地 SQLite，都是毫秒级。
- Akka.NET、Proto.Actor、Orleans：解决的是分布式、监督树、消息序列化，一个进程一个主播用不上，还多一个大依赖。没有选。
- Redux 式的单一状态树（.NET 里的 Fluxor）：每个命令要一个 action、一个 reducer、一个 effect，样板多；reducer 先改状态，和“数据库先写成功再改状态”正好反着。没有选。
- 事件溯源：逻辑写成纯函数好测，但要把现有的表转成事件，0.3.x 起的数据都要升级过去；区域里的状态类本来就是普通的同步类，能直接 new 出来测。没有选。
- TPL Dataflow 的 `ActionBlock` 当队列：运行时自带，但委托里有一个异常没接住，整个块就不再处理后面的消息。用 `Channel` 加一个消费循环更直白。没有选。
- 不单独做门面，在状态类上直接加 public async 方法：GUI 照样碰不到状态，但 Core 里别的类拿着对象就能绕过区域直接调同步方法，迁移时编译器也找不出原来那几处跨区域的直接调用（`LotteryFeature` 调 `lottery.Receive`、`GiftRecording` 调 `board.Take`、解码器读 `WebService.Video.Settings`）。门面只多几个类的外壳，转发的那几十行两种做法都要写。没有选。
- 让 GUI 直接写 `区域.Run(s => ...)`：“一步”漏进 GUI，GUI 的代码跑在区域的线程上，容易碰到界面对象。没有选。
- 订阅名单留一把自己的小锁，新订阅者先拿区域的快照：同一次变化可能推给新订阅者两次，以后每个接收方都得容忍；每个推送的区域还得多维护一份快照。没有选；登记和退订也是一步，和原来在锁里登记一样不漏不重。

## Consequences

- 写 Core 的代码守这几条：
  1. 一步里只碰本区域的状态，只做本地 SQLite 和内存操作；网络请求和等待放在外面。
  2. 一步里不 await，两个标了 `[Obsolete(error: true)]` 的重载挡住 async lambda；Core 里不写 `.Wait()`、`.Result`、`GetAwaiter().GetResult()`，smell-check 用 grep 查。
  3. 一步里要别的区域做事只用 `Post`，不用 `Run`；投递的函数只捕获不可变的数据，不捕获本区域的状态。这样一步永远不会等另一个区域，区域之间不会互相卡死。
  4. 要求先后的跨区域操作，由发起方按顺序 await。
  5. 外面的流程每次从一步回来，按当时的状态判断。
  6. 区域可以公开不可变的“最新快照”只读属性，任何地方都能读，读到的是最近一步结束时的值。
  7. 投递的步骤自己接住预期的异常、写清楚日志；漏网的由区域记一条错误日志，然后接着执行下一步。区域停了以后，投递的直接丢掉，等结果的抛取消异常。
  8. `deferred: true` 只用于只读事务。
  9. 从加锁迁过来时，一个 `lock` 块翻成一步，不合并、不拆开：锁外的代码本来就按“状态随时会变”写，翻过来照样成立。
  10. 状态对象只交给区域；状态类的构造函数和实例方法是 internal，GUI 和 Core 里的其他类只通过门面。
  11. 推送只在步骤里发；登记、退订订阅也是步骤。
- 最容易出 bug 的是区域和别的并发方式混在一起的地方：区域外面的异步流程、每个推流软件连接上的写锁、SQLite 自己的锁。一项对 15 个大型 Scala actor 程序的研究发现，八成程序把 actor 和别的并发方式混用，死锁和数据竞争多出在这种地方（Tasharofi 等，ECOOP 2013）。审查每一处改动都先查两件事：有没有在一步之外碰状态，有没有在一步里等别的东西。
- 跨区域没有全局顺序。同一个来源交给同一个区域的步骤按顺序执行；一步里投递的，在这一步结束前已经排进对方的队列，之后才发生的事一定排在它后面。两个互不相关的来源谁先到谁先做，和原来抢锁一样。
- 礼物分两步走：收消息的循环先在礼物榜区域分期，再在直播间连接区域写收礼记录、记进发送队列。中间礼物榜可能已经结束，和原来锁里给期号、锁外写库一样。盲盒统计要的那份写失败，照旧结束直播间连接。
- 要几个区域一起才能做的决定，放进一个区域，让别的区域把事件投递或推送过去，例如桌宠决定抽奖揭晓时要不要鼓掌。
- 一步慢只拖住它自己的区域。最重的一步是礼物榜连上时读出这个直播间所有礼物的 tid，原来它卡住收消息，现在只让礼物分期稍等。
- 关窗和测试只等一处：所有区域还有几步没做完的计数归零。
- 同一个进程里几个区域可能同时写 SQLite：写事务一开始就拿写锁，由 SQLite 排队，原来 GUI、收消息和计时器也是同时写的。
- GUI 不再同步读 Core 的状态，改用订阅或第 6 条的快照；每个功能多一层只做转发的门面。
